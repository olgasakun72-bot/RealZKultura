[X] УЯЗВИМО: конкатенация строк

// legacy-app v0.9 — ровно то, что работает на стенде
var sql = "SELECT * FROM users "
          + "WHERE login = '" + req.body.login + "' "
          + "  AND password = '" + req.body.password + "'";
db.query(sql);

// подстановка "' OR '1'='1" превращает запрос в:
// WHERE login = '' OR '1'='1' AND password = '' OR '1'='1'
// -> истина при любых данных -> доступ выдан

[V] ЛЕЧЕНИЕ: параметризованный запрос

// значение никогда не становится частью кода запроса

//   $st->execute([':l' => $login]);
+---ЧЕК-ЛИСТ ЗАЩИТЫ (по слоям)---+ defense in depth
  1. Параметризованные запросы / prepared statements — единственная настоящая защита от инъекции. Экранирование кавычек её не заменяет: оно зависит от кодировки и контекста и регулярно обходится.
  2. ORM с безопасным режимом. Сырой SQL в ORM (raw queries, extra(), literal()) возвращает вас в уязвимый режим — такие места помечайте в код-ревью.
  3. Валидация входа по белому списку: тип, длина, допустимый набор символов. Не «запретить плохое», а «разрешить только хорошее».
  4. Принцип наименьших привилегий для учётки БД. Приложению не нужны DROP, GRANT и доступ к служебным таблицам.
  5. Хранение паролей: argon2id или bcrypt с солью. MD5 и «plaintext» из дампа выше — отдельный инцидент, а не мелочь.
  6. Одинаковый ответ на любую неудачу входа. Разные сообщения для «нет такого пользователя» и «неверный пароль» — это oracle для перебора.
  7. Журналирование и алерты: фиксировать неудачные входы, серийные попытки, появление SQL-метасимволов в полях форм. Именно так инъекцию видно до ущерба.
  8. WAF — последний слой, а не первый. Правила по сигнатурам из списка выше ловят шум, но не заменяют исправленный запрос.

Проверка результата: после исправления прогоните тот же payload на стенде и убедитесь, что он ушёл в параметры как строковое значение, а не как фрагмент SQL.

[ АУДИТ ] // МИНИМАЛЬНЫЙ СЕТЕВОЙ ЧЕК-ЛИСТ

+---network-audit.checklist---+ только для систем, которыми вы владеете или на которые есть письменное разрешение 
## ПЕРЕД НАЧАЛОМ РАБОТ
[ ] Есть письменное разрешение владельца (scope, окно, контакты, стоп-слово).
[ ] Определены границы: какие хосты/подсети в scope, какие — вне.
[ ] Есть план отката и способ остановить тест за 60 секунд.
[ ] Согласовано, кому и в каком виде уходит отчёт.

## ИНВЕНТАРИЗАЦИЯ (пассивная, без воздействия)
[ ] Список публичных сервисов и их версий.
[ ] Сертификаты: срок, цепочка, совпадение имени, наличие wildcard.
[ ] Заголовки ответов: HSTS, X-Content-Type-Options, CSP, Referrer-Policy.
[ ] Открытые порты и соответствия заявленной архитектуре.
[ ] Утечки в журналах сборки: source maps, .git, .env, backup-файлы.

## КОНФИГУРАЦИЯ
[ ] Дефолтные учётные данные отсутствуют везде, включая принтеры и камеры.
[ ] Админ-панели не доступны из публичной сети без VPN/allowlist.
[ ] Автообновление включено, есть реестр зависимостей (SBOM).
[ ] Резервные копии существуют, отделены от сети, восстанавливались на практике.

## ЖУРНАЛИРОВАНИЕ
[ ] Логи не перезаписываются локально, уходят в отдельное хранилище.
[ ] В логах нет паролей, токенов и полных номеров карт.
[ ] Настроены алерты: массовые 401/403, новые админы, изменение правил firewall.
[ ] Время синхронизировано (NTP), часовой пояс единый.

## ПО ИТОГАМ
[ ] Каждой находке присвоена критичность и владелец.
[ ] У каждой находки есть воспроизводимый шаг и конкретная контрмера.
[ ] Назначена дата повторной проверки закрытых пунктов.
